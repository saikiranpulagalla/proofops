# ProofOps V1.0.0-rc4 — Failure/Fix Report

RC4 is the repair release for the final RC3 adversarial audit. It adds no new agent capability.

## 1. Promotion receipts could be structurally valid but semantically empty
**Failure:** RC3 verified signature/source/run/deployment identity but did not independently enforce each gate's DONE metrics.
**Fix:** central `validate_gate_metrics()` now enforces PostgreSQL concurrency booleans, Sheets verified readback/stale-version/version delta, Gmail verified sent proof + ACCEPTED authoritative evidence, Gemini scenario/trial/critical/overall/containment thresholds, and E2E UNKNOWN/reconciliation/restart/no-duplicate/accepted-zero-send requirements.

## 2. Claimed approval could authorize a safe retry indefinitely
**Failure:** `CLAIMED` authorization remained valid forever if payload was unchanged and no goal deadline existed.
**Fix:** `ApprovalService` now has a bounded continuation TTL (live default 900s, allowed 60–3600s). Expiry atomically marks the old approval `EXPIRED`, moves RETRYABLE action back to `APPROVAL_REQUIRED`, and run to `WAITING_APPROVAL`. A new approval preserves the same logical-effect identity.

## 3. Stale API idempotency could mistake run existence for mutation success
**Failure:** crashed approve/execute request could become permanently "recovered" although the requested mutation never happened.
**Fix:** recovery is route-specific. Approve requires durable matching approval proof; execute requires claimed authorization/effect evidence and routes crossed boundaries to resume/reconciliation; otherwise the stale request lease is safely reclaimed.

## 4. Empty Gmail-thread binding masqueraded as provider proof
**Failure:** `[]` was treated as verified Gmail absence despite no provider read.
**Fix:** empty binding now emits `operator_assertion` provenance and a distinct `operator_asserted_no_prior_conversation` evidence type. It is never represented as Gmail-provider proof.

## 5. Newer outbound mail could hide older inbound customer truth
**Failure:** newest message in authoritative thread could be a ProofOps/team reply, causing older customer ACCEPTED/DNC truth to be ignored.
**Fix:** authoritative threads are read directly and business interpretation selects the newest usable **verified inbound customer** message; outbound/third-party messages cannot mask it.

## 6. Qualification recipient guard remained operator-configurable
**Failure:** a real address could theoretically be placed into the allowlist.
**Fix:** `PROOFOPS_QUALIFICATION_MODE=YES` requires the authenticated Gmail sender to be the only allowed recipient and every synthetic CRM contact to equal that mailbox. The final E2E checks the same condition again.

## 7. Deployment/source proof did not fully bind executable environment
**Fix:** receipts now include runtime-environment fingerprint plus exact deployment artifact SHA-256. Deployment fingerprint includes HTTPS/browser security settings, session TTL, request size, continuation TTL, qualification mode, restart mechanism identity and deployed base URL.

## 8. Promotion evidence was not independently verifiable after process exit
**Fix:** ephemeral HMAC remains for same-process receipt anti-mixing, but final promotion evidence is additionally Ed25519 signed using an external release private key. The public key fingerprint is pinned externally; `verify_v10_promotion.py` validates the persisted manifest later. The private key is never packaged.

## 9. Final live E2E was too happy-path and restart was in-process
**Fix:** the E2E wrapper commits a real Gmail send then deliberately throws `GmailOutcomeUnknown`; ProofOps must surface UNKNOWN and reconcile the original Message-ID with one physical message. Promotion additionally requires an external restart command, waits for deployed `/ready/providers`, checks the deployment artifact digest after restart, reads the old run from the deployed API, repeats the goal with no duplicate, and runs a second real ACCEPTED customer scenario that must create zero outbound action.

## Regression policy
Every repair is covered by a dedicated RC4 test and the complete historical suite remains green. No schema change was introduced; Alembic head remains `0008`.
