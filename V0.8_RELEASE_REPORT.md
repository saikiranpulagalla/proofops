# ProofOps V0.8.0 Release Report

## Purpose

V0.8 proves that the individually qualified components compose into one durable workflow without weakening the four original safety invariants or the later freshness/cross-run guarantees.

## New architecture

1. Create durable run.
2. Resolve exactly one CRM customer/renewal.
3. Read current Gmail customer evidence.
4. Persist run-scoped CRM/Gmail evidence.
5. Bind immutable workflow type, customer, renewal, GoalContract and snapshot to the run.
6. Ask the planner for a typed plan.
7. Validate/compile the plan deterministically.
8. Generate the outbound draft from trusted template/context, not model-controlled recipient fields.
9. Apply policy and move to `WAITING_APPROVAL`.
10. Bind approval to run + action + actor + payload.
11. Re-read CRM/Gmail immediately before the effect; material drift invalidates approval and blocks the send.
12. Execute through the existing effect ledger.
13. On ambiguous outcome: `UNKNOWN -> RECONCILING`; never blind retry.
14. Persist verified Gmail evidence.
15. Evaluate GoalContract from durable evidence and transition to `COMPLETED_VERIFIED` only when proof is sufficient.

## Schema change — 0005

V0.8 allows evidence with `action_id/effect_id = NULL` so business observations can exist before a side effect. It also adds durable run context:

- workflow_type
- subject_customer_id
- subject_renewal_id
- goal_contract_json
- snapshot_json

A run/evidence/source uniqueness constraint prevents duplicate evidence records without forcing unrelated runs to share evidence.

Legacy V0.7 evidence remains valid. The migration does not invent context for old runs; new context columns stay nullable for legacy rows.

## Composition bugs found and fixed during V0.8

### Split clock false-UNKNOWN
Effect evidence used a separate wall clock from GoalContract evaluation. In deterministic/replay tests this made valid sent evidence appear future-dated. `EffectExecutor` now accepts the same injected clock as the workflow for business evidence/reconciliation time.

### Duplicate goal after successful outreach
A global logical effect key correctly prevented a second action but the second run used to collide rather than converge. V0.8 now recognizes a prior `CONFIRMED` logical outreach, imports its verified transport proof as run-scoped evidence, and resolves the second run with no second send.

### Duplicate goal while original effect is uncertain
A second run is blocked while the prior logical action is `UNKNOWN`/otherwise unresolved. It cannot create an independent send path.

### Deadline passed while waiting for approval
The previous composition could have sent and only later failed GoalContract completion. V0.8 rechecks the deadline immediately before effect claim; expired approval context is revoked/blocked and zero provider calls occur.

### Material evidence changed after approval
CRM version/contact/status/DNC or relevant Gmail intent drift invalidates the prior approval. The exact previously approved payload cannot cross a changed business state.

## Offline demo result

The demo intentionally makes the provider commit an email and then lose the response. First result:

`run=UNKNOWN action=UNKNOWN physical_messages=1`

After reconciliation:

`run=COMPLETED_VERIFIED action=CONFIRMED physical_messages=1`

A second identical renewal goal then ends as:

`COMPLETED_NO_ACTION_REQUIRED physical_messages=1`

This is the core V0.8 claim: uncertainty and repeat submission do not silently create duplicate external effects in the tested model.
