# 3. WHY THIS PROJECT IDEA WAS CHOSEN

The objective is not to build another chatbot.

The project is meant to demonstrate what actually makes an autonomous agent trustworthy:

> An AI may propose the work, but deterministic software owns identity, policy, authorization, side effects, reconciliation, evidence and completion.

The workflow is deliberately narrow so we can prove deep reliability.

Primary scenario:

> A user gives ProofOps a high-level business goal involving a customer's subscription renewal.

Example:

> "Make sure ACME's renewal is handled by Friday without contacting them unnecessarily."

The system should determine business truth from applications, decide whether outreach is needed, prepare an action, ask for human authorization when needed, perform it safely, verify the real-world effect, recover from uncertain outcomes, and prove the final result.

A narrow renewal workflow was chosen because it gives judges visible evidence of:

- high-level goal handling;
- AI planning;
- multi-app use;
- business-data reasoning;
- persistent state;
- human approval;
- consequential external action;
- fault recovery;
- idempotency;
- evidence-based completion;
- repeat-run behavior;
- security boundaries.

That is more valuable under this rubric than six shallow integrations.

# 7. KEY SAFETY / RELIABILITY INVARIANTS

Treat these as hypotheses to verify in actual code.

Every one should be attacked.

## I1 — No silent entity guessing

If the target business entity cannot be resolved exactly and unambiguously:

```text
no consequential action
```

Duplicate/ambiguous customers must not cause arbitrary selection.

---

## I2 — Evidence is not authority

Email bodies, Sheet cells and other external data may contain malicious instructions.

External evidence can inform business facts.

It must not gain control of:

- tool choice;
- recipient selection;
- policy;
- authorization;
- credentials;
- arbitrary execution.

---

## I3 — LLM has bounded authority

Gemini should not directly:

- send email;
- mutate CRM;
- create arbitrary tools;
- choose unapproved recipients;
- declare success;
- bypass deterministic policy.

---

## I4 — Exact approval binding

Human authorization must bind the exact consequential payload.

Canonical payload hash must prevent:

```text
approve A
execute B
```

Any material change must require fresh authorization.

---

## I5 — Fresh business truth at effect boundary

Immediately before a consequential action:

- business state must be refreshed;
- meaningful drift must be compared semantically;
- eligibility must be re-evaluated;
- approval must be invalidated when assumptions changed.

CRM version alone must not be the safety boundary.

---

## I6 — User goal constrains actions

The stored natural-language goal must not be ornamental metadata.

Examples:

```text
"Do not contact ACME"
```

must make external outreach impossible.

```text
Goal says BETA
structured company says ACME
```

must fail closed / require human correction.

At the same time:

```text
"handle ACME renewal without contacting them unnecessarily"
```

must NOT be interpreted as a blanket no-contact prohibition.

The goal-intent parser therefore needs high precision.

---

## I7 — No external effect before durable state

Before provider code can execute, durable storage must already represent the attempt.

A crash must never create:

```text
provider may have been called
+
no durable effect record
```

---

## I8 — UNKNOWN means UNKNOWN

When provider outcome cannot be proven:

```text
do not call it success
do not blindly retry
```

Reconcile first.

---

## I9 — Deterministic effect identity

Logical consequential action identity must remain stable across retries/restarts.

For Gmail, deterministic RFC Message-ID or equivalent external identity is used to reconcile potential committed sends.

---

## I10 — No duplicate external effects

The classic failure:

```text
Gmail commits
↓
response lost
↓
agent blindly resends
```

must never create two physical messages.

---

## I11 — Provider response is not completion proof

A provider response alone should not mark business completion.

Expected pattern:

```text
send
↓
read back / reconcile
↓
persist verified evidence
↓
only then CONFIRMED
```

---

## I12 — No false COMPLETED_VERIFIED

A run is allowed to become completed only when its GoalContract/postconditions are actually proven by accepted evidence.

---

## I13 — Cross-run evidence isolation

Evidence from another run/customer/renewal must not accidentally satisfy this run's postconditions.

---

## I14 — Crash convergence

Every accepted durable state should have a valid recovery path.

Especially attack crashes:

- before run initialization;
- during RESOLVING;
- after context binding;
- after planning;
- after approval creation;
- after approval claim;
- before effect creation;
- after effect creation but before provider;
- during provider;
- after provider commit;
- before provider response;
- after response but before evidence persistence;
- during reconciliation;
- after confirmation before completion;
- during HTTP idempotency bookkeeping.

No legal state should become a permanent zombie.

---

## I15 — API idempotency is causal, not approximate

A stale HTTP mutation request must only recover the durable mutation caused by THAT request.

Timestamp correlation is insufficient.

Particularly inspect approvals and `api_request_id`.

---

## I16 — Authorization time is part of authorization identity

A 30-second approval and a 3600-second approval are not interchangeable merely because actor/action/payload are identical.

No request may silently inherit a broader authorization lifetime.

---

## I17 — Same logical goal cannot duplicate work

Repeated same-renewal goals must converge to existing state instead of producing another consequential effect.

---

## I18 — Operator assertion != provider proof

If "no prior Gmail conversation" is supplied as configured knowledge, it must remain explicitly labeled as an operator assertion.

Never claim Gmail proved absence unless Gmail actually proved the condition.

---

## I19 — Live qualification is self-send-only

Qualification must never accidentally message a real customer.

Synthetic CRM contacts used for final effects must resolve to the authenticated dedicated Gmail test account.

---

## I20 — Release promotion must not false-green

A receipt containing `"PASS"` is not sufficient.

The central validator must independently enforce DONE conditions and metrics.

## RC4 failures that were found

Examples included:

- signed PASS receipts could have weak metrics;
- `CLAIMED` retry authorization could remain valid indefinitely;
- stale HTTP idempotency recovery could infer mutation success too loosely;
- empty Gmail thread configuration could masquerade as Gmail-proven absence;
- latest outbound email could hide an earlier inbound ACCEPTED customer truth;
- qualification recipient allowlist could potentially include unsafe recipients;
- promotion evidence was not independently verifiable after the process exited;
- initial E2E/restart proof was too weak.

RC4 introduced or strengthened:

- central gate metric validation;
- bounded approval-continuation TTL;
- mutation-specific stale HTTP recovery;
- explicit `operator_assertion` provenance;
- newest verified inbound customer-message semantics;
- self-send qualification;
- Ed25519 persisted promotion signing;
- stronger response-loss E2E.

## RC5 failures that were found

Important crash/release findings:

### Crash window

Old sequence:

```text
approval CLAIMED
Action PREPARED
Run EXECUTING
↓ crash
no effect row
```

could strand the run.

RC5 changed new execution so:

```text
approval claim
+
run/action execution transition
+
first effect-attempt creation
```

cross the DB boundary atomically before Gmail becomes callable.

### Legacy PREPARED recovery

Old RC4 `PREPARED + CLAIMED + no effect` rows received explicit upgrade recovery.

### Partial create-run recovery

A crash after `Run` creation but before initialization could be incorrectly considered idempotently recovered.

RC5 added durable immutable initialization input and resumable:

```text
CREATED
RESOLVING
PLANNING
```

initialization.

### Deployment E2E

RC5 moved consequential live E2E operations through the deployed HTTPS app rather than only an in-process TestClient.

### Provider readiness

Expensive provider readiness became authenticated and sanitized.

### Restart/artifact proof

RC5 introduced boot identity and stronger deployment attestation, although later audits found further issues.

## RC6 failures that were found and supposedly fixed

### User goal authority

Problem:

```text
goal_text = "Do not contact ACME"
```

could still produce/send email.

RC6 introduced deterministic `GoalIntent`, expected to distinguish high-confidence prohibitions and subject conflicts.

### Semantic CRM drift

Same-version changes such as:

```text
renewal_date → +120d
renewal_date → past
renewal_date → None
company ACME → NOT-ACME
```

previously crossed approval.

RC6 should compare material business meaning and rerun eligibility instead of trusting version only.

### Approval TTL semantics

Different approval windows must not silently share an existing approval.

### Approval recovery causality

Approvals now should carry exact `api_request_id` provenance.

### Multi-worker restart

Process-local boot IDs were insufficient.

RC6 should now use a shared durable deployment generation.

### Release/runtime source identity

Full release source and stripped runtime payload now have separate identities.

### Login throttling

RC6 adds shared DB-backed failed-login throttling.

All of these MUST be independently verified.

- reproduction command/test/script;
