## Promotion evidence model

All live receipts are bound to:

- RC label and package version
- exact Alembic head
- one qualification run id
- exact source-tree SHA-256 fingerprint
- one deployment SHA-256 fingerprint computed only from non-secret deployment identity/configuration
- gate-specific target SHA-256 fingerprint
- gate metrics
- HMAC-SHA256 signature using an ephemeral promotion key

The signing key exists only in the promotion process environment and is not stored in the receipt bundle or final promotion evidence.

The promotion command validates every receipt after all five gates finish. A missing, altered, stale, mixed-build, mixed-run or mixed-deployment receipt blocks promotion.

## Final live promotion command

After configuring the dedicated synthetic deployment and secrets:

```bash
python scripts/promote_v10.py --execute-live \
  --google-token "$PROOFOPS_GOOGLE_TOKEN_FILE" \
  --spreadsheet-id "$PROOFOPS_SHEETS_SPREADSHEET_ID" \
  --customer-id "$PROOFOPS_E2E_CUSTOMER_ID" \
  --renewal-id "$PROOFOPS_QUALIFICATION_RENEWAL_ID"
```

This runs:

1. non-network preflight with live prerequisites required
2. real PostgreSQL schema + concurrency qualification
3. real synthetic Sheets mutation/readback/restore
4. Gmail self-send + authoritative renewal-thread evidence qualification
5. Gemini semantic/containment qualification
6. full real-provider end-to-end run, cold restart and repeat-goal no-duplicate check

Only then is `qualification/v1.0/V1.0_PROMOTION_EVIDENCE.json` written with `promotion_status=READY_FOR_V1.0_TAG`.

## Promotion rule

If the five live gates pass without code changes, tag the **exact RC3 source** as final V1.0; do not rebuild or modify it between qualification and tagging. If any live-discovered issue requires source changes, create RC4 and rerun the offline + live qualification sequence.
