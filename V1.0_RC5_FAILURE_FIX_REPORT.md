# ProofOps V1.0.0-rc5 — Failure/Fix Report

RC5 repairs the final RC4 adversarial findings without adding new agent capability.

## 1. Approval could be CLAIMED while no durable effect existed
**Failure:** a crash after approval claim but before `start_attempt()` could strand `Run=EXECUTING`, `Action=PREPARED`, `Approval=CLAIMED`, with no effect row.

**Fix:** first execution now uses `claim_approval_and_start_attempt()` as one database transaction. Approval claim, run/action transitions, and creation of the first `EXECUTING` effect lease commit atomically. Gmail cannot be called before the durable effect exists. Legacy RC4 `PREPARED/no-effect` rows remain recoverable.

## 2. Legacy PREPARED/no-effect recovery could strand on deadline/drift
**Fix:** legacy rows are explicitly handled. If continuation is still valid, ProofOps safely continues the same logical effect. If the goal deadline expires or business truth drifts before any provider attempt exists, the approval is expired and the action/run terminalize without a Gmail call. If continuation authorization expires, the same logical action reopens human approval.

## 3. Partially created runs could be falsely idempotently recovered
**Failure:** an API crash after inserting the Run row could later return a recovered `CREATED` run and mark the HTTP request complete even though workflow initialization never finished.

**Fix:** run initialization input (`company`, optional deadline) is durably and immutably checkpointed in `runs.initial_request_json` (Alembic 0009). `resume()` now advances `CREATED`, `RESOLVING`, and `PLANNING`. Legacy RC4 rows without this field may bind it once only from an exact idempotent retry whose request hash already matches the durable API-request record.

## 4. Restart proof could be satisfied by a no-op command
**Fix:** every app process receives a fresh boot ID at startup. Qualification captures the pre-restart boot ID and requires a different boot ID after the external restart while source/environment/deployment fingerprints remain unchanged.

## 5. Artifact identity was previously self-attested
**Fix:** final qualification requires `PROOFOPS_DEPLOY_ARTIFACT_ATTEST_COMMAND`, an external mechanism that emits the digest of the actual running artifact/image. The result must match the expected deployment SHA-256 before and after restart. `/health` no longer treats an environment variable as artifact proof.

## 6. The consequential live E2E used an in-process TestClient
**Fix:** final qualification now performs create, approve, execute, UNKNOWN observation, reconciliation/resume, post-restart read, repeat goal, and existing-ACCEPTED zero-send scenario through the deployed HTTPS API. A qualification-only server-side Gmail wrapper commits the real send and deliberately loses the first response so the deployed service must prove `UNKNOWN -> reconciliation -> CONFIRMED` with exactly one physical message.

## 7. Deployed configuration was not fully attested
**Fix:** an authenticated qualification-only attestation endpoint exposes only non-secret release identity: version, Alembic head, boot ID, source fingerprint, runtime-environment fingerprint and deployment-configuration fingerprint. Promotion compares these values against the qualification process before and after restart.

## 8. Provider readiness was publicly expensive/noisy
**Fix:** `/ready/providers` requires an authenticated session and returns sanitized failure status only. Public `/health` and `/ready` remain cheap liveness/internal-readiness endpoints.

## 9. Qualification harness regression protection
A new RC5 kill suite covers atomic effect-start durability, legacy PREPARED recovery, deadline terminalization with zero send, resumable partial run creation, legacy initialization backfill, boot-ID attestation, qualification endpoint visibility, one-shot response-loss injection, E2E promotion metrics and external artifact mismatch rejection.
