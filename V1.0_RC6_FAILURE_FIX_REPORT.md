# ProofOps V1.0.0-rc6 — Failure/Fix Report

RC6 is a release-hardening-only candidate. It adds no new provider or product capability.
It closes the RC5 adversarial findings around user-intent authority, pre-effect business
freshness, approval temporal/causal identity, deployment-generation proof, runtime-source
attestation, and login throttling.

## 1. Explicit user no-contact intent could be ignored

**Failure:** `goal_text` was stored but did not deterministically constrain the GoalContract or planner. A user could say "Do not contact ACME" while the structured company field still caused a renewal email plan.

**Fix:** RC6 adds a deliberately narrow, high-precision deterministic `GoalIntent` compiler. Explicit no-contact/no-email prohibitions become `NO_EXTERNAL_CONTACT`; obvious company-subject contradictions become `SUBJECT_CONFLICT`. The workflow blocks subject conflicts before action creation, carries goal constraints into the persisted contract/planning context, and the deterministic validator independently rejects `SEND_RENEWAL_OUTREACH` under `NO_EXTERNAL_CONTACT`.

**Regression protection:** the original demo wording, "without contacting them unnecessarily", is explicitly tested and is not treated as a blanket prohibition.

## 2. Same-version CRM semantic drift could cross approval

**Failure:** pre-effect refresh relied too heavily on CRM version discipline. Company or renewal-date changes could occur without a version bump and still cross the approval boundary.

**Fix:** RC6 compares the full material business snapshot and re-runs time-sensitive business eligibility immediately before the effect. Company, contact, renewal identity/status/date, DNC, version, email intent/recent-message identity, and conflicts participate in semantic drift detection. Missing/past/out-of-window renewal dates fail closed. CRM evidence source IDs are content-addressed so legitimate same-version observations remain immutable rather than colliding.

## 3. Approval TTL was not part of authorization identity

**Failure:** a second approval request with a different TTL could inherit an existing active approval with a different authorization window.

**Fix:** an active approval is reused only for the same causal API request, or for a direct non-API call with the exact same expiry window. A different authorization request/window returns a conflict instead of silently widening or narrowing authority.

## 4. Stale approval idempotency recovery could bind a later approval

**Failure:** stale approve recovery inferred causality from `created_at`, so an older crashed request could recover a different approval created later by another request.

**Fix:** approvals now carry an optional unique `api_request_id` foreign key (Alembic `0010`). HTTP approval creation binds that exact request ID. Stale recovery only accepts an approval caused by the same durable API request.

## 5. Multi-worker boot IDs could create a false restart proof

**Failure:** process-local `boot_id` values differ across workers, so a load-balanced request hitting another worker could look like a restart.

**Fix:** RC6 adds a PostgreSQL-backed `deployment_boots` generation keyed by the deployment fingerprint. Every worker reports the shared current generation. Final qualification requires the shared generation to advance after the explicit deployment restart; landing on another existing worker no longer proves restart.

## 6. Full release-source identity and stripped runtime identity were conflated

**Failure:** the offline release hash intentionally includes tests/Docker/deployment templates, while the runtime image intentionally omits them. Expecting those layouts to share one hash is incorrect.

**Fix:** RC6 separates:
- `release_source_fingerprint` — complete executable/qualification release source;
- `runtime_payload_fingerprint` — exactly the `app/`, `scripts/`, `alembic/`, `pyproject.toml`, and `alembic.ini` runtime payload.

`release_identity.json` freezes both. A stripped runtime must recompute and match the runtime payload hash while carrying the frozen release-source identity. A full source checkout also recomputes and verifies the release-source hash.

## 7. Public login had no shared throttling

**Failure:** repeated failed login attempts had no application-level rate limit.

**Fix:** RC6 adds DB-backed login throttling shared across workers, with configurable bounded failure/window/lockout settings. A successful login clears the throttle state after the lockout/window permits another attempt.

## Schema

Alembic `0010` adds:
- `approvals.api_request_id` with unique FK to `api_requests`;
- `deployment_boots` for shared deployment generations;
- `login_throttles` for shared login-rate state.

Legacy RC5 approvals migrate with `api_request_id = NULL`; no authorization is invented.
